## 阶段 1：采集遇到风控立即停止

- 修改 `lib/bili/collect.mjs`：评论或字幕读取出现 RATE_LIMITED、RISK_CONTROLLED、统一暂停或预算耗尽时，立即停止后续网络请求。
- 返回已经取得的结果、明确的停止原因、恢复时间（如有）和未处理视频；未完成的当前视频也要有明确状态，避免被漏出未处理范围。
- AUTH_REQUIRED 停止该批次并提示重新登录；普通单条内容错误仍允许继续。
- 单测断言错误出现后请求计数不再增加，且部分结果和剩余范围正确。

## 阶段 2：统一读取调度与持久化熔断

- 新增 `lib/bili/traffic-guard.mjs`，复用现有私有数据目录、原子写入和跨进程锁；接入 `lib/bili/http.mjs` 的实际传输入口。
- 同一数据目录共享 API 发送间隔和并发上限；实际发送前再次检查暂停状态，防止排队请求穿透熔断。锁作用域和等待必须有界，并响应取消。
- 按 DedeUserID 隔离账号预算；缺少 ID 时使用凭据摘要作为回退，匿名单独分组；不持久化原始凭据。
- HTTP 412/429 与已有明确风控分类触发共享 API 暂停：5、10、20、30 分钟递增，取平台 Retry-After、业务 pauseMs 和本地暂停中最长值。不自动重发失败请求。
- 区分平台全局风控与私信等接口局部配额，局部配额只阻断对应写入类别；不因单个权限错误冻结全部接口。
- 验证码要求进入人工处理状态；登录过期阻断受认证请求并允许扫码恢复，不能把恢复入口一起锁死。
- 状态损坏拒绝放行，跨日/时间窗口、时钟变化、进程退出和旧写限流状态迁移都要有明确处理；不得丢弃旧暂停时间。
- API 与媒体分开计数：图片、字幕文件、弹幕文件及 DASH/ffmpeg 不消耗 API 写额度。审计直接 fetch 和 ffmpeg 路径，明确各路径覆盖范围，避免媒体切片误耗 API 预算。

## 阶段 3：预算、写入分级与可见状态

建议首版默认值：

| 类别 | 本地限制 |
| --- | --- |
| API 读取 | 发送间隔 1.5 秒，并发 1；每账号 600/小时、3000/天 |
| 账号写入总预算 | 12/小时、30/天，跨工具和进程共享 |
| 评论、动态发布 | 同时受账号总间隔 120 秒约束 |
| 私信 | 类别间隔 60 秒，并受账号总间隔约束 |
| 点赞、收藏、稍后观看、删除和上传 | 保留最低 3 秒间隔，受总预算和平台暂停约束 |

- 发布、私信的账号总间隔与类别间隔取最大值，不通过换工具规避；上传和发布分别按真实请求计数，文档明确一次工具可能消耗多次额度。
- 预算在实际发送前持久化预留；已发送失败也计数，不能靠失败重置预算；仅明确未发送的预留可释放。
- 读取命中风控后同时阻止后续账号写入；平台暂停期间 check 也不绕过限制，继续保留未决账本。
- 统一返回 resumeAt、暂停原因、作用范围、剩余额度；本地预算或暂停不诱导 Agent 立即重试。保持原有错误码与平台原话的兼容性，明确 retryable 的延后重试语义。
- 在现有 CLI 增加只读状态查询和人工恢复命令；人工恢复不能清空预算或缩短仍有效的平台暂停。扫码后验证登录状态再清除相应登录阻断。
- 首版使用集中默认策略，暂不扩展设置页；如后续支持配置，必须有校验和最低保护边界。
