## 1. Token：渲染层代理

同一批固定返回值（extract 190 条字幕 + 60 条弹幕 + 40 条评论、transcribe 30 段、inspect 9 帧），分别用 baseline 的缩进 JSON 和 candidate 的 `renderText` 生成模型可见文本：

| 指标 | baseline | candidate | 比例 |
| --- | ---: | ---: | ---: |
| 字符 | 47,704 | 15,937 | **0.334** |
| 字节 | 62,984 | 31,427 | **0.499** |
| 粗略 token（字符级估算） | 15,802 | 10,933 | **0.692** |

T1/T2 的渲染压缩是明确的，但**这不是 DSH 会话 token**：最终 M1 仍需按 `docs/eval/token-bench-task.md` 在宿主内用真实 token 统计复测。粗略 token 的降幅明显小于字符降幅，因为 JSON 的英文键名/标点仍占 token。

## 2. ASR CER

方法：平台字幕在窗口内的文本为参考，ASR 输出同窗口文本为假设。归一化 = NFKC + 小写 + 去掉空白/标点/符号；这会同时去掉 `C++` 的 `+`，报告里按“字符内容”比较。CER = 编辑距离（Unicode 码点）/ 参考码点数。候选和基线使用同一低码率音轨、同一窗口、同一模型。

| 视频 | 窗口 | 参考字符 | baseline CER | candidate CER | 候选配置 | 备注 |
| --- | --- | ---: | ---: | ---: | --- | --- |
| BV1KDNA6eEgr | 60–120s | 402 | 0.3333 | **0.2015** | prompt+hotwords | 基线首段文本对应约 72s 的字幕，60–72s 内容未出现在输出中；疑似窗口内偏移/漏转写，需 cue 级复核 |
| BV1KDNA6eEgr | 180–240s | 386 | **0.1684** | 0.5907 | prompt+hotwords | 候选只输出 1 段（210–240s），漏了 180–210s；重跑结果完全一致 |
| BV1REx46NEc4 | 120–180s | 413 | **0.2300** | 0.2567 | prompt+hotwords | 候选略差 |

三窗口平均：baseline `0.2439`，candidate `0.3496`。候选整体更差，且 180s 窗口是可复现的严重回归。

### 180s 消融（同一 WAV）

先从低码率音轨抽出 180–240s 的同一个 WAV，再分别跑 baseline 与 candidate 的不同提示配置，排除音轨/下载差异：

| 版本/配置 | 段数 | CER | 耗时 |
| --- | ---: | ---: | ---: |
| baseline（无额外提示） | 20 | **0.1684** | 30.3s |
| candidate：prompt + hotwords | 1 | 0.5907 | 70.5s |
| candidate：仅 prompt | 24 | 0.2021 | 38.8s |
| candidate：不额外传（仍有内置简体引导句） | 26 | 0.1891 | 26.1s |
| candidate：仅 hotwords（同一 WAV） | 3 | 0.5699 | 79.3s |

结论：**同一 WAV 下，hotwords 单独或与 prompt 同时传入都会严重退化**（1–3 段，CER 0.57–0.59）；prompt-only 0.2021、none 0.1891、baseline 0.1684。早先一次“hotwords-only 0.1736”用的是不同 WAV，不能作为安全性证据。最可能的原因是 faster-whisper 1.2.1 的 `hotwords` 与长 prompt/解码窗口的交互 bug，或 hotwords 合并后超过提示预算；需要按版本和长度进一步隔离。这是修复前的行为；修复后见下节。修复前即使只用 prompt，180s 窗口 CER 仍高于 baseline（0.2021 vs 0.1684），A1 的收益也未被证明。

### A1 修复后验证

修复内容：`bilibili_transcribe` 不再向 ASR 传 `hotwords`，只保留受控 prompt；`asrHints()` 单测锁定只返回 prompt（不覆盖工具层全链路）；ASR 缓存 key 补上 `decoder`/`hints`，decoder 版本升到 3，避免命中旧 hotwords 缓存。

| 窗口 | baseline CER | 修复后 candidate CER | candidate 段数/耗时 |
| --- | ---: | ---: | --- |
| BV1KDNA6eEgr 60–120s | 0.3333 | **0.1542** | 16 段 / 31.4s |
| BV1KDNA6eEgr 180–240s | **0.1684** | 0.1788 | 26 段 / 66.6s |

修复后不再出现“1 段/0.59”的灾难性退化；60s 窗口明显优于 baseline，180s 窗口略差（0.1788 vs 0.1684），耗时仍约 2 倍。当前保留 prompt-only，但它不是无条件收益，需在 M2 更多窗口上确认；hotwords 暂不恢复。

### A5 置信度

候选的 `lowConfidence` 标注不一致：60s 窗口 12/13 段被标低置信（但 CER 只有 0.2015），180s prompt-only 26 段全部未标低置信。阈值（logprob -1.0、compression 2.4、no_speech 0.6）尚未校准，不能直接作为“这段不可信”的证据。

## 3. 结论

- **T1/T2 token 渲染**：值得继续；先补 DSH 真实 token 计量，再决定是否合入。
- **A1 ASR 提示**：hotwords 已从工具路径移除，修复后不再出现灾难性退化；prompt-only 在 60s 窗口明显更好（0.1542 vs 0.3333），180s 略差（0.1788 vs 0.1684），需要更多窗口确认净收益。
- **A3/A5**：A3 的 `condition_on_previous_text=False` 与 A5 低置信阈值的影响还未分离；当前证据不足以证明收益。
- **整体计划**：基础评测已能区分“渲染省 token”和“ASR 精度回归”。A1 的 hotwords 已移除；下一步补 M2 到至少 6 个有字幕视频 × 每视频 2 窗口，再决定 prompt-only 是否默认保留。

## 4. 复现

```bash
# 渲染代理（baseline 与 candidate 各一次）
node tests/eval/render-bench.mjs --root /tmp/bili-baseline --baseline
node tests/eval/render-bench.mjs --root .

# ASR：先抽同一个 WAV，再让 baseline/candidate 复用
# BILI_DATA_DIR 需指向含 credentials.json/config.json 的临时目录
node tests/eval/prepare-asr-window.mjs --root . --bvid BV1KDNA6eEgr --start 180 --duration 60 --out /tmp/window-180.wav
for mode in both prompt hotwords none; do
  node tests/eval/asr-cer-direct.mjs --root . --bvid BV1KDNA6eEgr --start 180 --duration 60 --hints "$mode" --wav /tmp/window-180.wav
done
node tests/eval/asr-cer-direct.mjs --root /tmp/bili-baseline --bvid BV1KDNA6eEgr --start 180 --duration 60 --hints none --wav /tmp/window-180.wav
```

不要记录 Cookie/Token；`--root` 只用于本地 worktree。
